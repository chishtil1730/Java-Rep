Unit 01
Product Metrics & Size-Oriented (LOC) Metrics
Foundations of measurement · LOC-based metrics · Advantages & limitations
1.1 What are Software Metrics?
Software Metric: A quantitative measure of a property of a piece of software or its specification. Metrics provide an objective, data-driven basis for making engineering decisions — estimating cost, managing risk, and improving quality.
Metric TypeWhat it MeasuresExamplesWhen Used
Product MetricsCharacteristics of the software artifactLOC, FP, V(G), HalsteadDuring & after development
Process MetricsSoftware development process qualityDRE, defect rate, rework %Ongoing process measurement
Project MetricsProject execution characteristicsCost variance, schedule varianceProject management
🎯 Exam Tip
Examiners frequently ask you to classify a given metric. Remember: Product = the thing built; Process = how it was built; Project = the project that built it.
1.2 Size-Oriented Metrics (LOC / KLOC)

Lines of Code (LOC) counts source statements, excluding blank lines and comments. KLOC = LOC ÷ 1000.

Core LOC-Based Formulas
Productivity = LOC Delivered / Person-Months
Errors per KLOC = Total Errors / (LOC / 1000)
Defects per KLOC = Total Defects / (LOC / 1000)
Cost per LOC = Total Project Cost / LOC
Doc pages per KLOC = Documentation Pages / (LOC / 1000)
AdvantageDisadvantage
Simple and universally understoodLanguage-dependent (Assembly vs. Python for same task)
Vast industry historical data availablePenalises concise, elegant code
Easy to automate (tool can count lines)Cannot be measured until coding phase — useless for early estimation
Basis for well-known cost models (COCOMO)Does not measure functionality delivered to the user
Solved Problem 1.1 — LOC Metrics Computation
A software project delivers 42,000 lines of code. During testing, 63 errors were found. After delivery, customers reported 7 defects. The project took 6 person-months and cost ₹12,00,000. Calculate: (a) Errors per KLOC, (b) Defects per KLOC, (c) Productivity, (d) Cost per LOC, and (e) DRE (preview).
▶ Step-by-Step Solution
1
Identify all given data:
LOC = 42,000 → KLOC = 42
Errors found in testing (E) = 63
Defects found by customer (D) = 7
Effort = 6 person-months, Cost = ₹12,00,000
2
(a) Errors per KLOC:
Errors per KLOC = Total Errors / KLOC = 63 / 42 = 1.5 errors/KLOC
This means on average 1.5 bugs exist per 1000 lines of code.
3
(b) Defects per KLOC (Defect Density):
Defect Density = Defects (post-delivery) / KLOC = 7 / 42 = 0.167 defects/KLOC
4
(c) Productivity:
Productivity = LOC / Person-Months = 42,000 / 6 = 7,000 LOC/person-month
5
(d) Cost per LOC:
Cost per LOC = Total Cost / LOC = 12,00,000 / 42,000 = ₹28.57 per LOC
6
(e) DRE (Defect Removal Efficiency — full formula in Unit 3):
DRE = E / (E + D) = 63 / (63 + 7) = 63 / 70 = 0.90 = 90%
This is below the industry benchmark of 95%, meaning 10% of defects escaped to customers.
Errors/KLOC=1.5 | DefectDensity=0.167 | Productivity=7000 LOC/PM | Cost/LOC=₹28.57 | DRE=0.90
Solved Problem 1.2 — LOC Language Dependency
Two teams implement the same feature. Team A (Java) produces 800 LOC in 2 months. Team B (Python) produces 250 LOC in 2 months. Compare productivity (LOC/month) and explain why LOC is a misleading productivity metric here.
▶ Solution
1
Calculate LOC productivity for each team:
Team A (Java): Productivity = 800 / 2 = 400 LOC/month Team B (Python): Productivity = 250 / 2 = 125 LOC/month
LOC-based metric suggests Team A is 3.2× more productive.
2
Why this is misleading:
Both teams delivered identical functionality in identical time. Python's high-level constructs compress what requires multiple Java statements into a single line. A metric that "rewards" Team A for writing verbose code is perverse — it penalises the more efficient language and programmer.
LOC/month: Java=400, Python=125. LOC metric is misleading — same functionality in same time is equally productive regardless of LOC count. Use Function Points for language-independent measurement.
Unit 02
Function Point Metrics
Albrecht's FP · UFP · VAF · Adjusted FP · Feature Points · 3D FP
2.1 Concept & Why Function Points?
Function Points (Albrecht, 1979): A measure of the amount of functionality delivered to the user, computed entirely from requirements — completely independent of the programming language. It overcomes LOC's language-dependence.
The Three-Step FP Calculation
Step 1: UFP = Σ (Count_i × Weight_i) ← Unadjusted Function Points
Step 2: VAF = 0.65 + 0.01 × ΣFi ← Value Adjustment Factor (Fi: 0–5 each)
Step 3: FP = UFP × VAF ← Final Adjusted Function Points
Domain CharacteristicSymbolSimple WeightAverage WeightComplex Weight
User Inputs (distinct input types)Inp346
User Outputs (reports, screens)Out457
User Inquiries (online query/response)Inq346
Files (logical master files)Fil71015
External Interfaces (machine-readable I/F)Int5710
🎯 Memory Trick for Weights
Inp/Inq: 3-4-6 | Out: 4-5-7 | Fil: 7-10-15 | Int: 5-7-10
Notice Inp and Inq share the same weights (3-4-6). Files have the highest weights because they represent persistent data — the most complex element. Write these in a table on your rough sheet before starting any FP problem.
Solved Problem 2.1 — Standard FP Calculation
An online banking system has: 12 user inputs (8 simple, 4 average), 8 user outputs (5 average, 3 complex), 6 inquiries (all average), 4 master files (2 average, 2 complex), 3 external interfaces (all simple). The sum of all 14 general system characteristics (ΣFi) = 52. Calculate UFP, VAF, and FP.
▶ Full Step-by-Step Solution
1
Map counts to the weight table:
Domain Count × Weight = Contribution ────────────────────────────────────────── Inputs: (8 × 3) + (4 × 4) = 24 + 16 = 40 Outputs: (5 × 5) + (3 × 7) = 25 + 21 = 46 Inquiries: (6 × 4) = 24 = 24 Files: (2 × 10)+ (2 × 15) = 20 + 30 = 50 Interfaces:(3 × 5) = 15 = 15 ────────────────────────────────────────── UFP Total = 175
2
Calculate VAF:
VAF = 0.65 + 0.01 × ΣFi = 0.65 + 0.01 × 52 = 0.65 + 0.52 = 1.17
VAF range is always 0.65–1.35. A VAF of 1.17 means the system is moderately complex (17% above baseline).
3
Calculate Final FP:
FP = UFP × VAF = 175 × 1.17 = 204.75 ≈ 205 Function Points
UFP = 175 | VAF = 1.17 | FP = 205
Solved Problem 2.2 — FP-to-LOC Conversion
A Java application is estimated at 320 Function Points. Historical data shows Java produces approximately 53 LOC per function point. Estimate (a) total LOC, (b) development effort if productivity is 800 LOC/person-month, and (c) project duration if 5 developers work in parallel.
▶ Solution
1
(a) Estimate LOC:
LOC = FP × LOC/FP rate = 320 × 53 = 16,960 LOC ≈ 17 KLOC
2
(b) Estimate Effort:
Effort = LOC / Productivity = 16,960 / 800 = 21.2 person-months
3
(c) Duration with 5 developers:
Duration = Total Person-Months / # Developers = 21.2 / 5 = 4.24 months
Note: This assumes perfect parallelism; in practice, Brooks' Law applies — adding more people to a late project makes it later.
LOC ≈ 16,960 | Effort ≈ 21.2 person-months | Duration ≈ 4.2 months

Unit 03
Metrics for the Requirements Model
DRE · Phase-level DRE · RSI · Requirements quality metrics
3.1 Defect Removal Efficiency (DRE)
DRE measures how effectively the team finds and removes defects before they reach the customer. A DRE of 1.0 is perfect (no escapes); industry best-in-class is ≥ 0.95.
DRE Formulas
Overall DRE : DRE = E / (E + D)
Phase DRE_i : DRE_i = E_i / (E_i + E_i+1)

Where:
E = defects found & removed BEFORE delivery
D = defects found BY CUSTOMER after delivery
E_i = defects found in phase i
E_i+1 = defects that escaped to next phase
Solved Problem 3.1 — Overall & Phase DRE
A project has the following defect history:
• Requirements review: 18 defects found
• Design review: 22 defects found
• Code inspection: 30 defects found
• System testing: 15 defects found
• Post-delivery (customer-reported): 8 defects

Calculate (a) Overall DRE, (b) DRE at each phase, and (c) interpret the results.
▶ Solution
1
(a) Overall DRE:
E = 18 + 22 + 30 + 15 = 85 (defects removed before delivery) D = 8 (customer-reported) DRE = E / (E + D) = 85 / (85 + 8) = 85 / 93 = 0.914 ≈ 91.4%
This is below the industry benchmark of 95%. About 8.6% of defects reached customers.
2
(b) Phase-level DRE:
Each phase's DRE = defects found in this phase ÷ (found here + found in next phase)
DRE_req = 18 / (18 + 22) = 18/40 = 0.45 (45%) — Requirements → Design DRE_design= 22 / (22 + 30) = 22/52 = 0.42 (42%) — Design → Code DRE_code = 30 / (30 + 15) = 30/45 = 0.67 (67%) — Code → Testing DRE_test = 15 / (15 + 8 ) = 15/23 = 0.65 (65%) — Testing → Delivery
3
(c) Interpretation:
• Requirements and design phases have the lowest DRE (42–45%), meaning more than half the defects from these phases slip through to the next. This suggests poor review quality early in the lifecycle.
• Improving requirement reviews could prevent expensive rework downstream.
• The overall 91.4% DRE needs improvement. Target: find 2 more defects during testing to achieve DRE = 87/(87+6) = 93.5%, approaching the 95% benchmark.
Overall DRE = 0.914 (91.4%). Weakest phase: Design review at 42%. Needs better early-lifecycle reviews.
3.2 Requirements Stability Index (RSI)
RSI Formula
RSI = 1 – (Number of requirement changes after baseline / Total requirements)

RSI → 1.0 = stable (good)
RSI → 0.0 = highly volatile (bad)
Solved Problem 3.2 — RSI Calculation & Impact
A project documented 80 requirements at baseline. During development, 12 requirements were modified and 5 new ones were added. Calculate RSI and comment on project risk.
▶ Solution
1
Identify total changes:
Total changes after baseline = 12 (modifications) + 5 (additions) = 17 Total baseline requirements = 80
2
Calculate RSI:
RSI = 1 – (17 / 80) = 1 – 0.2125 = 0.7875 ≈ 0.79
3
Interpret:
RSI = 0.79 indicates moderate volatility — about 21% of requirements changed after the baseline was set. This introduces schedule and cost risk. A well-managed project should aim for RSI ≥ 0.90. The team should consider a formal change-control board to triage future requirement changes.
RSI = 0.79 — Moderate volatility. 21% requirement churn poses schedule risk.
Unit 04
Metrics for the Design Model
Cohesion · Coupling · Cyclomatic Complexity · OO Metrics
4.1 Cohesion & Coupling
Cohesion — Best → Worst
  • ⑦ Functional — one task only
  • ⑥ Sequential — output feeds next
  • ⑤ Communicational — shared data
  • ④ Procedural — fixed sequence
  • ③ Temporal — same time
  • ② Logical — logically similar
  • ① Coincidental — random grouping
Coupling — Best → Worst
  • ① Data — simple params only
  • ② Stamp — shared composite struct
  • ③ Control — passes control flag
  • ④ External — shared protocol/device
  • ⑤ Common — shared global data
  • ⑥ Content — direct internal access
🎯 Mnemonic
Cohesion worst→best: "Can Larry Tell People Correct Software Facts?" (Coincidental, Logical, Temporal, Procedural, Communicational, Sequential, Functional)
Coupling best→worst: "Data Stamp Control External Common Content" → D-S-C-E-C-C
Solved Problem 4.1 — Identify Cohesion Type
Classify the cohesion type for each module below:
(a) Module printReport() — reads data, formats it, and sends it to the printer.
(b) Module init() — opens DB connection, loads config file, initialises cache, and sets global flags — all at startup.
(c) Module calculateTax(income) — returns the tax amount for a given income.
(d) Module processIO(flag) — if flag=1 reads file; if flag=2 writes file; if flag=3 reads network.
▶ Solution
a
printReport() — reads → formats → prints. The output of one activity feeds the next. This is Sequential Cohesion (Level 6).
b
init() — all tasks happen together at system startup but are unrelated to each other. This is Temporal Cohesion (Level 3). They are grouped only because they execute at the same time.
c
calculateTax(income) — performs one and only one well-defined task. This is Functional Cohesion (Level 7) — the highest and most desirable.
d
processIO(flag) — logically similar operations (all I/O) selected by a flag. This is Logical Cohesion (Level 2). The caller must pass a control flag, which also implies control coupling.
a=Sequential | b=Temporal | c=Functional | d=Logical
4.2 Cyclomatic Complexity V(G) — McCabe
Cyclomatic Complexity V(G) counts the number of linearly independent paths through source code. It directly determines the minimum number of test cases needed for path coverage.
Three Equivalent Formulas
Formula 1: V(G) = E − N + 2P
Formula 2: V(G) = Number of predicate nodes + 1
Formula 3: V(G) = Number of regions in the planar graph

E = edges, N = nodes, P = connected components (usually = 1)
Predicate node = any node with a binary decision (if, while, for, case)
V(G) RangeInterpretationRiskAction
1 – 10Simple, well-structuredLowAcceptable
11 – 20Moderate complexityMediumReview recommended
21 – 50Complex, hard to testHighRefactoring advised
> 50Untestable, very high riskVery HighMust refactor
Solved Problem 4.2 — V(G) from Control Flow Graph
Calculate V(G) using all three formulas for the following pseudocode and draw the control flow graph mentally (nodes listed below):

1. START
2. Read score
3. IF score ≥ 90 THEN grade = 'A'
4. ELSE IF score ≥ 75 THEN grade = 'B'
5. ELSE IF score ≥ 60 THEN grade = 'C'
6. ELSE grade = 'F'
7. Print grade
8. END
▶ Solution — All Three Methods
1
Identify the CFG structure:
Nodes (N): N1 = START + Read score N2 = Decision: score ≥ 90? ← predicate node N3 = grade = 'A' N4 = Decision: score ≥ 75? ← predicate node N5 = grade = 'B' N6 = Decision: score ≥ 60? ← predicate node N7 = grade = 'C' N8 = grade = 'F' N9 = Print grade + END Total Nodes N = 9 Edges (E): N1→N2, N2→N3(true), N2→N4(false), N3→N9, N4→N5(true), N4→N6(false), N5→N9, N6→N7(true), N6→N8(false), N7→N9, N8→N9 Total Edges E = 11
2
Formula 1 — E − N + 2P:
V(G) = E − N + 2P = 11 − 9 + 2×1 = 11 − 9 + 2 = 4
3
Formula 2 — Predicate nodes + 1:
Predicate nodes = N2, N4, N6 = 3 V(G) = 3 + 1 = 4
4
Formula 3 — Regions in planar graph:
Regions = 3 enclosed regions + 1 outer region = 4
5
Enumerate the 4 Independent Paths:
Path 1: N1→N2(T)→N3→N9 (score ≥ 90, grade='A') Path 2: N1→N2(F)→N4(T)→N5→N9 (75≤score<90, grade='B') Path 3: N1→N2(F)→N4(F)→N6(T)→N7→N9 (60≤score<75, grade='C') Path 4: N1→N2(F)→N4(F)→N6(F)→N8→N9 (score<60, grade='F')
V(G) = 4 tells us we need minimum 4 test cases for complete path coverage.
V(G) = 4 by all three methods. 4 independent paths → minimum 4 test cases needed. Risk: Low.
Solved Problem 4.3 — V(G) with Loop
Calculate V(G) for: WHILE (i < 10) DO { IF (a[i] > max) THEN max = a[i]; i++; }
▶ Solution using predicate method
1
Identify predicate (decision) nodes:
Decision 1: WHILE condition — (i < 10)? ← predicate Decision 2: IF condition — (a[i] > max)? ← predicate Total predicate nodes = 2
2
Apply Formula 2:
V(G) = Predicate nodes + 1 = 2 + 1 = 3
3
The 3 independent paths are:
P1: Loop never executes (i ≥ 10 initially) P2: Loop executes, a[i] ≤ max (inner IF is false) P3: Loop executes, a[i] > max (inner IF is true, max updated)
V(G) = 3. Three test cases cover all paths: empty loop, loop with no update, loop with update.

Unit 05
Architectural Design & Halstead Metrics
Structural Complexity · Data Complexity · Halstead's Software Science
5.1 Structural Complexity Metrics
Architectural Complexity Formulas
Structural Complexity: S(i) = fan_out(i)²
Data Complexity: D(i) = i / (fan_out(i) + 1) [i = I/O parameters]
System Complexity: SC = Σ [ S(i) + D(i) ] for all modules i
Solved Problem 5.1 — Structural, Data & System Complexity
A software system has 4 modules with the following structure-chart data:
Module A: fan-out=3, I/O params=6
Module B: fan-out=2, I/O params=4
Module C: fan-out=4, I/O params=8
Module D: fan-out=1, I/O params=2
Calculate S, D, and total System Complexity SC.
▶ Solution
1
Calculate S(i) = fan-out²:
S(A) = 3² = 9 S(B) = 2² = 4 S(C) = 4² = 16 ← highest structural complexity S(D) = 1² = 1
2
Calculate D(i) = i / (fan-out + 1):
D(A) = 6 / (3+1) = 6/4 = 1.50 D(B) = 4 / (2+1) = 4/3 = 1.33 D(C) = 8 / (4+1) = 8/5 = 1.60 D(D) = 2 / (1+1) = 2/2 = 1.00
3
System Complexity SC = Σ(S + D):
Module A: S+D = 9 + 1.50 = 10.50 Module B: S+D = 4 + 1.33 = 5.33 Module C: S+D = 16 + 1.60 = 17.60 ← most complex Module D: S+D = 1 + 1.00 = 2.00 ──────────────────────────────────── SC = 10.50 + 5.33 + 17.60 + 2.00 = 35.43
Module C has the highest complexity (17.60) — it should be targeted first for refactoring or testing effort.
S: A=9, B=4, C=16, D=1 | D: A=1.50, B=1.33, C=1.60, D=1.00 | SC = 35.43
5.2 Halstead's Software Science Metrics
Halstead (1977): Predicts effort, time, and bug count purely from token counts in source code — no execution needed. Operators are symbols/keywords; operands are variables/constants.
Halstead Derived Metrics — All Formulas
Inputs: η₁ = distinct operators, η₂ = distinct operands
N₁ = total operators, N₂ = total operands

Vocabulary: η = η₁ + η₂
Length: N = N₁ + N₂
Est. Length: N̂ = η₁·log₂η₁ + η₂·log₂η₂
Volume: V = N × log₂η (bits of information)
Difficulty: D = (η₁/2) × (N₂/η₂)
Effort: E = D × V (mental discriminations)
Time: T = E / 18 (seconds)
Bugs: B = V / 3000 (or E^(2/3)/3000)
Solved Problem 5.2 — Complete Halstead Analysis
Analyse the following C code segment using Halstead metrics:

int max(int a, int b, int c) {
  int m = a;
  if (b > m) m = b;
  if (c > m) m = c;
  return m;
}

Identify all operators and operands, then calculate η, N, V, D, E, T, and B.
▶ Step-by-Step Token Analysis
1
List all OPERATORS (symbols & keywords that act on data):
Operators identified: int, =, if, >, return, () [function call/def], {} [block] Also counting: , [parameter separator] Distinct operators (η₁): int, =, if, >, return, (, ), {, }, , η₁ = 10 distinct operators Total operator occurrences (N₁): int → appears 4 times (return type + 3 params) = → appears 3 times (m=a, m=b, m=c) if → appears 2 times > → appears 2 times return → appears 1 time ( ) → appears 3 times (function header + 2 ifs) { } → appears 1 time , → appears 2 times N₁ = 4+3+2+2+1+3+1+2 = 18
2
List all OPERANDS (variables and constants):
Distinct operands (η₂): max, a, b, c, m η₂ = 5 distinct operands Total operand occurrences (N₂): max → 1 (function name) a → 3 (param + m=a + if a) → actually: a appears in param decl, m=a, b>m uses m... Let us recount carefully: a → parameter decl (1), m = a (1) = 2 b → parameter decl (1), if(b > m) (1), m = b (1) = 3 c → parameter decl (1), if(c > m) (1), m = c (1) = 3 m → int m (1), m=a (1), b>m (1), m=b (1), c>m (1), m=c (1), return m (1) = 7 max → function name (1) = 1 N₂ = 2+3+3+7+1 = 16
3
Calculate Basic Metrics:
η₁ = 10, η₂ = 5 N₁ = 18, N₂ = 16 Vocabulary: η = η₁ + η₂ = 10 + 5 = 15 Length: N = N₁ + N₂ = 18 + 16 = 34
4
Volume V = N × log₂(η):
log₂(15) = log(15)/log(2) = 1.176/0.301 = 3.907 V = 34 × 3.907 = 132.8 bits
5
Difficulty D = (η₁/2) × (N₂/η₂):
D = (10/2) × (16/5) = 5 × 3.2 = 16.0
High difficulty (16) means operands are reused often — operand 'm' alone appears 7 times.
6
Effort E, Time T, Bugs B:
E = D × V = 16.0 × 132.8 = 2,124.8 mental discriminations T = E / 18 = 2,124.8 / 18 ≈ 118 seconds ≈ 2 minutes B = V / 3000 = 132.8 / 3000 ≈ 0.044 (essentially 0 expected bugs)
η=15 | N=34 | V=132.8 | D=16.0 | E=2124.8 | T≈118s | B≈0.04 (very clean, simple function)
Solved Problem 5.3 — Halstead vs. McCabe: Which to Use When?
Compare Halstead and McCabe metrics and explain when each is more appropriate. Give an example where one metric paints a different picture than the other.
▶ Answer
1
Fundamental difference:
Halstead = counts tokens (operators & operands) → measures SIZE & EFFORT McCabe = counts decision nodes in CFG → measures CONTROL COMPLEXITY
2
Example — mathematical formula function:
double compound_interest(double P, double r, int n, int t) { return P * pow((1 + r/n), n*t); }
McCabe V(G) = 1 (no decision points — perfectly simple by McCabe's measure)
Halstead V = high (many distinct operators: *, +, /, pow, etc. and operands reused)
McCabe says "trivial" but Halstead correctly captures that this formula has cognitive complexity.
3
When to use which:
Use McCabe V(G) when: planning test cases, assessing branch coverage, identifying modules that need refactoring due to too many decision branches. Use Halstead when: estimating programming effort early (before full code), predicting likely bug counts, assessing cognitive load of data manipulation code.
Halstead measures computational complexity; McCabe measures control-flow complexity. Both are complementary — use together for a full picture.

Interpret:

6.3 Reliability Metrics — MTTF, MTTR, MTBF, Availability
Reliability Formulas
MTTF = Total operating time / Number of failures
MTTR = Total repair time / Number of repairs
MTBF = MTTF + MTTR
Availability (A) = MTTF / (MTTF + MTTR) × 100%

Where: MTTF = Mean Time To Failure | MTTR = Mean Time To Repair MTBF = Mean Time Between Failures (for repairable systems)
Solved Problem 6.2 — Comprehensive Reliability Analysis
A banking server runs 24×7. Over 6 months (4,380 hours), it experienced 6 failures. The repair times for the 6 failures were: 2h, 3h, 1h, 4h, 2h, 3h. Calculate MTTF, MTTR, MTBF, Availability. Is the system meeting a 99% availability SLA?
▶ Solution
1
Total repair time and MTTR:
Total repair time = 2+3+1+4+2+3 = 15 hours Number of repairs = 6 MTTR = 15 / 6 = 2.5 hours per repair
2
MTTF — operating time between failures:
Total time window = 4,380 hours Total downtime = 15 hours (sum of all repair times) Total operating (up) time = 4,380 − 15 = 4,365 hours MTTF = Total operating time / # failures = 4,365 / 6 = 727.5 hours
3
MTBF:
MTBF = MTTF + MTTR = 727.5 + 2.5 = 730 hours
The system fails on average every 730 hours (~30 days).
4
Availability:
A = MTTF / (MTTF + MTTR) × 100% = 727.5 / (727.5 + 2.5) × 100% = 727.5 / 730 × 100% = 99.66%
5
SLA check:
99.66% > 99% SLA target ✓. The system is meeting its availability SLA. However, one long repair (4h) is pulling MTTR up — reducing that single event would push availability even higher.
MTTF=727.5h | MTTR=2.5h | MTBF=730h | Availability=99.66% ✓ (meets 99% SLA)
Solved Problem 6.3 — Finding Missing Values
A system has MTBF = 200 hours and Availability = 96%. Find MTTF and MTTR.
▶ Algebraic Solution
1
Set up equations from known formulas:
MTBF = MTTF + MTTR → MTTF + MTTR = 200 ... (i) Availability = MTTF / MTBF 0.96 = MTTF / 200 MTTF = 0.96 × 200 = 192 hours ... (ii)
2
Solve for MTTR:
From (i): MTTR = MTBF − MTTF = 200 − 192 = 8 hours
MTTF = 192 hours | MTTR = 8 hours

Set A — Function Points
  1. A payroll system has: 15 inputs (10 simple, 5 average), 10 outputs (6 average, 4 complex), 8 inquiries (all simple), 5 files (3 average, 2 complex), 4 external interfaces (2 simple, 2 average). ΣFi = 40. Find UFP, VAF, FP.
  2. Two projects, A (C language, 65 LOC/FP) and B (Python, 21 LOC/FP), both estimated at 250 FP. Calculate the LOC for each and explain why FP is a better cross-project comparison tool.
  3. A system has FP=400. Historical data: effort = 0.0022 × FP¹·¹. Calculate effort in person-months.
▶ Show Answers
1. UFP=(10×3+5×4)+(6×5+4×7)+(8×3)+(3×10+2×15)+(2×5+2×7) = 50+58+24+60+24 = 216; VAF=0.65+0.40=1.05; FP=216×1.05=226.8≈227
2. A: 250×65=16,250 LOC | B: 250×21=5,250 LOC — same functionality, 3× the code in C. FP measures what user gets, not how much code was written.
3. E = 0.0022 × 400^1.1 = 0.0022 × 566.9 ≈ 1.25 person-months

  1. A CFG has E=18, N=14, P=1. Find V(G) and classify risk.
  2. Code: if(x>0) { if(y>0) { z=1; } else { z=2; } } else { if(w>0) { z=3; } else { z=4; } } — Find V(G) by predicate method. List all paths.
  3. A module has V(G)=12. How many test cases are needed for full path coverage? What does this value indicate?
▶ Show Answers

2. Predicates: x>0, y>0, w>0 → V(G)=3+1=4; Paths: x>0∧y>0(z=1), x>0∧y≤0(z=2), x≤0∧w>0(z=3), x≤0∧w≤0(z=4)

Set C — Halstead Metrics
  1. η₁=7, η₂=10, N₁=25, N₂=30. Calculate V, D, E, T, B.
  2. Two modules: Module X (V=500, D=8) and Module Y (V=200, D=20). Which has higher effort E? Which is harder to understand?
  3. A program has Volume V=800. If it takes a programmer 55 minutes to understand it, what would Halstead predict for T? Are they consistent?
▶ Show Answers
1. η=17, N=55, V=55×log₂17=55×4.087=224.8; D=(7/2)×(30/10)=3.5×3=10.5; E=10.5×224.8=2360; T=2360/18=131s; B=224.8/3000=0.075

3. Halstead T=800×D/18 (need D). If T=55min=3300s, then E=T×18=59400; D=E/V=59400/800=74.25. Halstead predicts a very high D=74 which seems unrealistically high — showing limits of the model for large programs.
Set D — Reliability Metrics
  1. A system ran for 2,000 hours and failed 8 times. Average repair time is 5 hours. Find MTTF, MTTR, MTBF, and Availability.

  3. Team A has DRE=0.92, Team B has DRE=0.97. If both teams produce 100 defects total, how many defects escape to customers for each team? Which team is better?
▶ Show Answers

Set E — Exam-Style Short Questions
  1. Define the term "software metric." Give one example each of a product, process, and project metric.
  2. What is the VAF range in function point analysis? What does a VAF of 0.65 vs 1.35 signify?
  3. A module has LCOM=0. What does this indicate about the class? Is this good or bad?
  4. List McCall's 11 quality factors grouped by their three perspectives.
  5. Explain why DIT (Depth of Inheritance Tree) increasing beyond 5 is generally considered problematic.
  6. State two advantages of Function Points over LOC as a size measure.
  7. What is the difference between MTTF and MTBF? In which type of system is MTBF more meaningful?
  8. A code has no if/while/for/switch statements. What is its Cyclomatic Complexity? How many test cases are needed?
▶ Show Answers
1. A quantitative measure of software property. Product: LOC; Process: DRE; Project: cost variance.
2. VAF ∈ [0.65, 1.35]. VAF=0.65 means complexity has minimal influence on FP; VAF=1.35 means very high complexity adds 35% to the FP count.
3. LCOM=0 means all methods share at least one instance variable → highly cohesive class. This is good.
4. Operations: Correctness, Reliability, Efficiency, Integrity, Usability, Survivability. Revision: Maintainability, Flexibility, Testability. Transition: Portability, Reusability, Interoperability.
5. Deep inheritance = long reasoning chains to understand any class. Changes in a base class cascade unpredictably. Testing coverage explodes. Harder to reuse subclasses independently.
6. Language-independent; measurable from requirements (before coding begins).
7. MTTF = time until first/next failure (all systems). MTBF = time between failures including repair time (repairable systems). MTBF is meaningful for servers, hardware, network systems.
8. V(G)=1 (no predicates → 0+1=1). Only 1 test case needed — one straight-line path.
